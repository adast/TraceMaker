# D170 — Exact routing acceleration with per-board CPU and CUDA ownership

## Context

Repeated cell/geometry queries and field dispatch overhead leave substantial routing time outside
productive A* expansions. We need faster single-board routing and throughput across independent boards
while retaining exact routed artifacts and deterministic work. Doc 05 §73 and doc 07 §9 describe the
maintained implementations; `bench/records/routing-acceleration/` records their validation.

## Decision

- Keep the original deterministic CPU route decisions and exact final geometric checks.
- Use explicit, independently tested CPU modules for row rasterization, queue ordering, packed stale
  keys, full cell-cost reuse, planar moves, zero-backed records and conservative routed bounds.
- Compute CUDA fields with integer warp scans and device-side convergence, with ordinary-kernel and
  CPU fallback paths. `--gpu-field-min-cells` remains an explicit backend-cutoff override.
- Export immutable fixed scenes through `Obstacles`, keyed by full context and unique revision.
  Refuse unsupported rule contexts and via probes. Never infer metadata through recursion or globals.
- Give each router a ready-only tile broker and each session RAII ownership of CUDA resources.
  Default geometry prefetch uses 64 scenes and 64-cell tile edges. A miss executes the CPU predicate.
- Provide `tracemaker-batch` with 1–256 independent board workers, private outputs and flushed progress.
  Each board uses one route thread and one variant. Keep rescue/explanation defaults; fixed-work
  benchmarks explicitly disable both. Select one GPU through normal CUDA visibility.
- Keep verification optional: `--verify-acceleration` compares accelerated values with CPU references
  and records positive activation counts. Never include that extra work in performance measurements.

## Alternatives

- GPU A* prototypes: the exact ordering/visibility synchronization did not provide a useful accepted
  speedup. The production branch retains CPU A*.
- A shared cross-board field service: the accepted direct-call design was simpler and faster in the
  completed study. Independent contexts avoid cross-board cache and cancellation coupling.
- Waiting for geometry tiles: ready-only consumption preserves CPU progress and deterministic cache publication.
- Source snapshots or generated source substitutions: normal maintained modules make ownership,
  interfaces, tests and build dependencies reviewable.

## Consequences

The batch interface adds throughput without changing routing semantics. Timing and prefetch hits can
vary while routed files and charged work remain exact. Unsupported cases retain CPU behavior.
CPU, single-board GPU and batch gains have different denominators and are reported separately.
Memory grows with active boards and cached scenes; a 256-worker API does not establish a 256-board
performance or memory guarantee. Benchmark records identify the measured implementation ancestor,
reference revision, binaries and input hashes; a later documentation commit does not relabel the code measured.
